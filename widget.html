About this prototype — real data, and one open design question
This is your actual draft SO-23675, and every code/qty below is pulled straight from the EAN, cf_pack_barcode/cf_pack_quantity, cf_inner_carton_tun/cf_inner_carton_qty, and cf_tun/cf_carton_qty fields you've now populated on MCB and MHPC-B. Nothing here is a placeholder anymore for these two items.

Notice MCB has Item + Pack + Outer Carton (no inner carton set), while MHPC-B has Item + Inner Carton + Outer Carton (no pack set) — exactly the "not every item needs all four levels" case, working correctly with real data.

Open question: in Zoho, both items sit on two separate order lines each (MCB: 200 + 20, MHPC-B: 48 + 12) — maybe a pricing split, maybe just how the test order was entered. This app merges them into one pick target per item, since that's how picking actually works on the floor. But Zoho tracks quantity_picked per line, not per item — so a real write-back needs a rule for splitting a merged pick back across the underlying lines (simplest: fill the first line to its ordered qty, then spill into the next). Worth confirming whether that's actually how you want it handled, or whether duplicate lines like this shouldn't happen in practice.

On "Complete pick," a live version would write back to each line's quantity_picked field (which Zoho Inventory already tracks internally — it's just not exposed in the native app's scan-to-pick flow).
